Open standard that defines a compact n self-contained way for securely tranmitting info bwn parties as a JSON OBJECT.
This is digitally signed.

In its compact form, JSON Web Tokens consist of three parts separated by dots (.), which are:

Header-type of the token,signing algorithm
{
  "alg": "HS256",
  "typ": "JWT"
}
Payload: claims- stmts about entity(user) and additional data
-> these r Base64Url encoded
{
  "sub": "1234567890",
  "name": "John Doe",
  "admin": true
}
Signature-To create the signature part you have to take the encoded header,
the encoded payload, a secret, the algorithm
USE: The signature is used to verify the message wasn't changed along the way
and AUTH-(verify that the sender of the JWT is who it says it is.)

jwt.verify()method:
The jwt.verify() method is the gatekeeper for JSON Web Tokens. Here’s exactly what it does:
  🔍 What jwt.verify() does
  Checks the signature

  It takes the token (incomingRefreshToken) and the secret (process.env.REFRESH_TOKEN_SECRET).

    It recalculates the signature using the header + payload and compares it with the signature inside the token.

    If they don’t match, the token is invalid (maybe tampered with).

    Validates expiration & other claims

    If the token has an exp (expiry), nbf (not before), or iat (issued at) claim, verify() enforces those rules.

    Example: if the token expired 10 minutes ago, verify() throws an error.

    Decodes the payload safely

    If the token passes signature + claim checks, verify() returns the decoded payload (e.g., { _id: "12345", role: "user" }).

    This is what you’re storing in decodedRefreshToken.

NOTE:
Cookies: names must match what the client expects ("refreshToken").

  JSON response: property names must match your API contract (refreshToken),
  even if your local variable is called newRefreshToken.

->ObjectId is the special type MongoDB uses for its default _id field.

->In Mongoose, you can access it via mongoose.Types.ObjectId.

->It represents a 12-byte unique identifier (timestamp + machine ID + process ID + counter).

->Every document in a collection gets one automatically unless you override it.

MULTIPART REQUEST:
-----------------

A multipart request is an HTTP request format used when you want to send files along with other data in the same request.
This is exactly what you're using with Multer.

Why is it called "multipart"?
Because the request is divided into multiple parts.

For example, suppose you're updating a task:

    title = "Build Login"
    status = "COMPLETED"
    file = design.pdf

A normal JSON request would look like:

    {
      "title": "Build Login",
      "status": "COMPLETED"
    }

But JSON isn't designed to directly carry an uploaded file.

So the browser can send the request as:

multipart/form-data

Conceptually:

      ┌─────────────────────────────────┐
      │ Part 1                          │
      │ title = "Build Login"           │
      ├─────────────────────────────────┤
      │ Part 2                          │
      │ status = "COMPLETED"            │
      ├─────────────────────────────────┤
      │ Part 3                          │
      │ file = design.pdf               │
      │ [actual binary file data]       │
      └─────────────────────────────────┘

That's why it's multipart — one request contains multiple parts.
CONNECTION:

Frontend / Client

    OBJECTID
    -----------------------------

With normal Mongoose queries, you generally DON'T need to manually convert IDs.

For example:
✅
Task.findById(taskId)

Mongoose can cast valid string IDs according to the schema.
Explicit conversion is commonly used in aggregation pipelines:
✅
$match: {
    _id: new mongoose.Types.ObjectId(taskId)
}

because aggregation pipelines don't always get the same automatic Mongoose casting.

Also:

✅req.user._id

is already an ObjectId when it comes from the Mongoose User document, so generally no need to do:

❌new mongoose.Types.ObjectId(req.user._id)

BUGS:
MONGOOSE SUPPORTS ASYNC PRE-HOOKS NATIVELY — NO NEXT NEEDED AS LONG AS YOU DON'T DECLARE THE PARAMETER. MIXING "DECLARES NEXT" + "IS ASYNC" IS THE ACTUAL BUG; PICK ONE STYLE, NOT BOTH.
```
    userSchema.pre("save", async function (next) {
    if (!this.isModified("password")) return;
    this.password = await bcrypt.hash(this.password, 8);
    });
```
Why it's broken: You've declared next as a parameter, which tells Mongoose "this middleware uses the callback pattern — wait for me to call next()." But you never call it. Every single .save() on a User document (register, password change, anything) will hang forever — the promise never resolves, no error, it just times out eventually (or hangs your request). This will make registration look "stuck" with no clear error, which is a nasty one to debug blind.

Fix — drop the next param entirely and let the async function's own promise resolve/reject:

```
    userSchema.pre("save", async function () {
    if (!this.isModified("password")) return;
    this.password = await bcrypt.hash(this.password, 8);
    });
```

BUG 2:
---------------------------

Will break your React integration — cookie config, auth.controller.js
javascript
const options = {
  httpOnly: true,
  secure: true,
};

This appears in login, logoutUser, and refreshAccessToken. secure: true means the cookie is only ever sent over HTTPS. Your React dev server (Vite, port 5173) will be talking to your backend (port 3000) over plain http://localhost — the browser will silently drop these cookies, so login will appear to "succeed" (200 response) but no session will actually persist, and every subsequent secured request will look logged-out. There's also no sameSite set, which matters once you're doing cross-origin fetch/axios with credentials: "include".

Fix — make it environment-aware:

javascript
const options = {
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: process.env.NODE_ENV === "production" ? "none" : "lax",
};

This is important to fix before we wire up the frontend, or auth will look broken for reasons that have nothing to do with the React code.

BUG  3:
-------------------
🔴 Critical for the frontend — CORS_ORIGIN=* will silently break login

Your app.js sets credentials: true on CORS and your auth cookies rely on the browser accepting them cross-origin.
 Per the CORS spec, browsers refuse to expose Access-Control-Allow-Origin: * responses when credentials: true/cookies are involved 
 this isn't a server error, the browser just blocks it client-side, silently.
  Your login request will look like it succeeded (you'll see a 200 in the Network tab) but the cookie never actually gets set, and the next secured request will look logged-out.
